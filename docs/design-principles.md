# 设计原则

文档类型：设计规范草案。更新日期：2026-11-09（Asia/Shanghai）。本文件是设计规则的维护来源；具体绑定和例外维护在[快捷键对照表](shortcut-map.md)，整体进展见 [README](../README.md#当前状态)。

## 目标与边界

**Same Intent, Same Shortcut：先建立稳定的操作语言，再逐步映射到各个 App。**

- 保留 macOS 通用快捷键。
- 同一意图在不同 App 中尽可能使用同一按键。
- 按键具有语义逻辑，方便记忆和推导。
- 优先使用 App 原生能力，避免不必要的插件。
- 不追求绝对统一，不牺牲高频操作效率。

这些原则用于指导新增和改动；App 已有的默认差异可以保留，不要求一次性重排所有快捷键。

## 1. 意图由动作、对象和范围共同定义

用“我要对什么做什么”描述操作，不用某个 App 的菜单名称作为跨应用定义。

| 要素 | 需要明确的问题 |
| --- | --- |
| 动作 | 查找、打开、关闭、切换、移动，还是聚焦？ |
| 对象 | 内容标签、窗格、窗口、文件，还是命令？ |
| 范围 | 当前内容、当前组、整个窗口、工作区，还是系统？ |
| 行为条件 | 按位置还是按最近使用顺序？焦点在哪里？是否创建新内容？ |

以上条件相符时才视为同一意图。例如，按名称打开文件可以跨编辑器复用；切换到右侧标签与切换到最近使用的标签要分别定义。聚焦右侧窗格与把当前标签移到右侧窗格也要分别定义。

查找不因都出现搜索框就合并：当前内容查找、跨文件全文搜索、按名称打开内容、搜索命令，各有独立意图。

## 2. 分清系统、共享意图和 App 专属操作

| 层级 | 职责 | 扩展规则 |
| --- | --- | --- |
| 系统与 macOS 通用约定 | 系统导航、窗口管理及通用编辑习惯 | 先核对并保留，新增映射避开这些绑定 |
| 跨应用共享意图 | 多个 App 中对象、范围和行为一致的操作 | 优先复用已确定的键位；有能力缺口时允许留空 |
| App 专属操作 | 只对特定工作流有意义的能力 | 优先原生默认；不强行在其他 App 中寻找对应项 |

共享意图不等于系统全局热键：通常由每个 App 在自身内部实现相同绑定。新增 App 时只接入它支持的意图，无需补齐全部功能。

同一 App 内可以按焦点区分行为，但应符合当前对象的直觉。涉及标签、窗格和窗口的导航必须标明层级，不能只写“向左”“下一个”。

## 3. 按键应成组，修饰键在组内保持一致

先选一个能承载相关操作的按键组合，再考虑其反向或变体。以下是新增绑定时的设计倾向，不是对所有原生快捷键的重新解释。

| 按键元素 | 使用倾向 | 约束 |
| --- | --- | --- |
| 字母 | 优先沿用熟悉约定，其次选择容易联想的动作或对象 | 不为凑英文首字母抢占高频键；一旦选定跨 App 保持稳定 |
| `← / →`、`↑ / ↓` | 空间方向或有序移动 | 一对操作使用同一组修饰键；聚焦与移动对象分开 |
| 数字 | 按可见位置直接定位 | 同一组数字指向同一种对象；不要混用标签和窗格 |
| `⌘` | 应用内常用命令的首选基础修饰键 | 优先保护已有通用绑定 |
| `⇧` | 在同一操作组内表达稳定关系，如反向或扩大范围 | 同一组只采用一种可解释的关系；不机械地给所有命令加 `⇧` |
| `⌥` | 基础动作的相关变体 | 先检查文字编辑与字符输入；不将它简单视为空闲键 |
| `⌃` | 沿用原生约定，或作为确有需要的独立操作组候选 | 检查系统、输入法及终端上下文，不预设为全局导航层 |

一个操作组内的“下一项 / 上一项”可以使用 `⇧` 表达反向；另一个组内可以用 `⇧` 表达范围扩大。规则以操作组为单位，不要求 `⇧` 在全系统只有一个含义。

独立操作组也可以采用固定的修饰键组合作为整体前缀。这是经冲突评估后的局部约定：必须明确组的用途并一起核对相关成员，不能凭空推断单个修饰键有某种业务含义。此时把前缀作为整体记忆，不再把其中的 `⇧` 解释成某个未定义基础动作的反向。新增前缀仍是候选，直到实际采用。

优先保持成对操作的对称性：前进 / 后退、上一个 / 下一个、移入 / 移出。绑定前要同时检查另一方向是否可用，避免后续用完全无关的按键补齐。

每项键位都要交代选择依据，并区分三种来源：macOS 通用约定、已有操作组的语义派生、App 惯例或本项目的局部选择。沿用原生可以降低学习与改动成本，但不能单凭“原生默认”证明适合推广；还要说明其他 App 的冲突和适配代价。字母联想可以辅助记忆，不能冒充官方设计来源，也不能为了补解释而把每个修饰键都说成有独立含义。

## 4. 有限的好按键留给高频意图

- 高频操作优先短、顺手、容易连续触发的组合；不以更多修饰键换取形式统一。
- 中低频操作可以通过原生命令面板或菜单调用，不必每个命令都分配直接快捷键。
- 新操作先复用现有意图，再扩展相关操作组，最后才新增独立组合。
- 跨 App 的基础操作优先采用各 App 都能原生表达的组合；多段快捷键可以留给支持它的 App 专属操作。
- 首版不预留大量空键位，不预设必须引入 Hyper 键或全局映射工具；出现具体缺口后再评估。

“保留扩展空间”主要依靠稳定的意图和操作组规则，而不是先占满键盘。

## 5. 冲突按明确顺序处理

1. **先保护系统与通用约定。** 新绑定不覆盖系统导航、输入法切换和通用编辑键；App 已有默认差异单独记录。
2. **再保护已形成习惯的高频操作。** 统一若导致更难按、更多步骤或明显误触，保留该 App 的例外。
3. **优先复用已确定的共享绑定。** 新 App 接入时先尝试适配，避免因一个新命令改动整套体系。
4. **其他情况优先保留原生默认。** 只有共享收益明确时才自定义，不为所有局部功能重排键位。

多个 App 的默认值不一致时，不单纯按多数投票：同时比较使用频率、已有习惯、改动范围和原生可配置性。

如果某个共享键已在该 App 中承担重要的不同意图，允许记录例外；如果该意图不存在，则留空。以后新增 App 专属绑定时，尽量避免主动复用已确定的共享键来表达不相关动作。

优先在 App 内配置。只有明确的能力缺口才考虑 macOS 菜单快捷键、映射工具或插件，并评估其作用范围和维护成本。

## 新增一个操作时怎么决定

依次回答以下问题，并把具体结论写入对照表；不为每个操作另建一份规则文档。

1. **意图是什么？** 写清动作、对象、范围，以及必要的排序和焦点条件。
2. **是否已有同一意图？** 有则复用目标键，记录新 App 的对应命令；不支持则留空。
3. **是否属于已有操作组？** 有则沿用该组的方向、反向或变体规则，成对评估。
4. **是否值得直接分配键位？** 按实际频率决定；低频操作优先通过已有入口调用。
5. **为什么选这个组合？** 记录属于哪种来源、为何优于相关替代方式；不能从字母推导的原生组合明确标为沿用惯例。
6. **是否存在冲突或效率损失？** 依本文件的冲突顺序处理，注明保留例外的具体原因，以及自定义绑定、脚本或插件的适配代价。
7. **是否通过本机验证？** 按[验证条件](shortcut-map.md#落地前验证条件)检查实际行为，再将候选转为已采用。

记录至少包括意图、目标键、各 App 的对应行为和必要例外；候选、已采用和已验证应明确区分。后续调整直接修订当前定义，历史验证保留其日期和边界。
