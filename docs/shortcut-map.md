## 当前统一建议

本节是目标键位及例外的维护来源，选键依据见[设计原则](design-principles.md)。除明确标注“已采用”的项外，其余仍是候选设计。

| 意图 | 目标键位 / 策略 | 适用 App | 记忆逻辑与例外 |
| --- | --- | --- | --- |
| 查找当前内容 | 保留 `⌘F` | 三个 App | Find；限定当前内容 |
| 跨文件全文搜索 | 保留 `⌘⇧F` | VS Code、Obsidian | 在查找基础上扩大范围；Chrome 网页搜索另列意图 |
| 替换当前内容 | 保留 `⌘⌥F` | VS Code、Obsidian | 沿用两者已有约定 |
| 恢复关闭的内容标签 | 保留 `⌘⇧T` | 三个 App | 同一恢复意图，已具备共同默认键 |
| 关闭当前内容标签 | 候选 `⌘W` | 三个 App | Obsidian 待核对；单标签窗口、弹窗及未保存内容需实测 |
| 调用命令面板 | 候选 `⌘⇧P` | VS Code、Obsidian | VS Code 保留；Obsidian 可先增加此绑定，核对冲突后再评估旧绑定 |
| 按名称查找并打开内容 | 首版保留各自默认 | VS Code、Obsidian | VS Code `⌘P`，Obsidian `⌘O`；保留原生高频习惯 |
| 新建空标签 | Chrome、Obsidian 保留 `⌘T` | Chrome、Obsidian | VS Code 保留符号搜索，不覆盖其高频能力 |
| 按可见顺序切换标签 | 待核对后选键 | 三个 App | 先确认是否限当前组，再选共同键；不把 `⌃Tab` 直接认定为统一 |
| 按最近使用顺序切换内容 | 保留 VS Code 原生行为 | 暂限 VS Code | 与按可见顺序切换分开；暂不为补齐能力引入插件 |
| 按数字定位 | 保留各自默认 | 三个 App | VS Code 为编辑器组，另两者为标签；不强行合并 |
| 导航历史 | 首版保留各自默认 | 待核对 | 不能覆盖文本移动或 VS Code 的缩进绑定 |
| 聚焦地址栏 | 保留 Chrome `⌘L` | Chrome | 专属意图；不用于替代文件搜索或命令调用 |
| 打开本周周记 | 已采用 `⌃⇧W` | Obsidian Haleon 仓库 | 实际入口为 QuickAdd: Open Weekly Notes；用户已设置，本机保存的绑定已核对，未进行真实按键实测 |
| 选中光标所在单词 | 已采用 `⌘D` | VS Code | 当前无选区时选中当前词；再次按下追加下一处匹配，进入多光标选择 |
| 从光标选到行末 | 已采用 `⌘⇧→` | VS Code | 用于从值的起点选中行末的完整值，例如 `abc-dft-qwe`；选区终点取决于行末位置 |

VS Code 文本选择约定于 2026-11-09 经用户确认采用。在 [test_file.txt](../test_file.txt) 的 `client_id = abc-dft-qwe` 示例中，光标位于 `abc` 前，值在行末且本行未折行时，使用选到行末的操作取得整个值，再按 `⌘C` 复制；值后还有其他内容时会一并选入。按默认单词边界，选词操作在 `abc` 处选中的是 `abc`。以上为已采用的 VS Code 操作，不代表 Obsidian 的适配已经应用。

`test_file.txt` 是已通过 `.gitignore` 排除的本机练习文件，不随仓库分发；其他环境可根据上面的示例自行创建。

用户随后明确要求 VS Code 与 Obsidian 的文本编辑统一，取代此前暂保留选词 / 删除差异的设计方向。完整的[正文编辑统一方案](text-editing.md)负责目标键位、配置片段、现有 QuickAdd 适配、Kimi 冲突处理和验证边界。方案已准备，尚未应用到实际配置；保留当前词边界，先前的分隔符调整建议不采用。

周期笔记组以已采用的周记键为起点，拟沿用 `⌃⇧` 作为整体前缀，以 D/W/M/Y 区分日、周、月、年。这是本项目的局部约定，不是 macOS 或 Obsidian 的默认语义，也不要求其他操作采用相同前缀。目前仅周记项已采用；其他成员保留为扩展候选，不自动分配或启用功能。选择该前缀的原因是研究时未发现相关成员被占用，并且可以保留 Command 系列的既有绑定；它并非由 Control 或 Shift 的单独含义推导而来。[2026-11-09 核对记录](records/2026-11-09-obsidian-shortcuts.md)维护当时的默认键、仓库配置、候选比较、用户设置后的补充核对及验证边界。

`⌘P` 在 macOS 通用约定中用于打印，但 VS Code 与 Obsidian 已有原生差异。首版保留这些既有差异，不把 `⌘P` 推广为跨 App 的统一键，也不改动 Chrome 的打印键。若未来要统一文件入口，需明确评估对打印习惯和 Obsidian 命令面板的影响。

“搜索打开标签”“按名称打开文件”“输入 URL / 网络查询”“全文搜索”目前分别维护；只有确认对象和预期结果一致后才考虑合并。Chrome DevTools 内的命令调用也不视为浏览器日常操作入口。

## 落地前验证条件

以下只维护本专题的验证方法，不代表已经执行：

1. 记录 App 版本、键盘布局、输入法、现有自定义绑定及相关扩展；Obsidian 按具体仓库核对。
2. 在 VS Code 的 Keyboard Shortcuts 中检查命令及 `when` 条件；在 Obsidian 的 Settings → Hotkeys 中检查绑定和冲突；Chrome 先核对菜单显示的实际键位。
3. 用三个标签 A、B、C，按 A → C → B 的顺序访问后测试切换，区分可见顺序和最近使用顺序；编辑器组与标签组另测，明确是否跨组。
4. 分别测试正文编辑、搜索框、命令面板及分栏焦点；Chrome 另测普通网页、网页编辑器和 DevTools。确认没有覆盖文字输入或高频命令。
5. 关闭与恢复操作使用临时文档，检查未保存内容、最后标签及弹窗的行为。
6. 实际调整前保留原配置或逐项记录原绑定；回退时仅撤销本次新增或改动，不清空其他自定义项。应用内验证成功后，注明日期、范围和未验证项。

原生配置入口参考：[VS Code 快捷键配置](https://code.visualstudio.com/docs/configure/keybindings)、[Obsidian Hotkeys](https://obsidian.md/help/hotkeys)。
